Abstract

This project builds a Machine Learning system that estimates whether a passage of text was generated by AI or written by a human. It follows the complete workflow required by the course: problem definition, data acquisition and quality checks, exploratory analysis, preprocessing, feature engineering, baseline and model development, hyperparameter tuning, evaluation, error analysis, interpretation and demonstration.

The primary data is the Kaggle AI vs Human Text dataset, with 487,235 labelled texts, of which 487,231 remained after cleaning. Using TF-IDF features and a stratified 70:30 split, a most-frequent baseline reached 62.76% accuracy. Multinomial Naive Bayes reached 97.92%, tuned Logistic Regression 99.70% and tuned Linear SVM 99.95%.

Testing on paragraphs known to be human then showed a problem that these scores had hidden: the original Logistic Regression recipe flagged two of three such paragraphs as AI. Error analysis traced this to the removal of stop words, training only on long essays, a fixed 0.5 threshold and a human class containing only student essays. The final model addresses each cause. It combines word and character TF-IDF features, trains on essays, short snippets, pre-AI blogs and BBC news, and uses an AI threshold of 0.65 chosen on validation data. On held-out data, false AI flags on short human essay snippets fell from 8.5% to 0.4%, and on short blog and news snippets from 4.3% to 0.1%, while 96.8% of full-length AI essays were still detected.

Runtime benchmarks show the final model is practical on a laptop: a 400-word text takes a median of 4.6 ms to score directly and 7.0 ms through the REST API, and the service uses about 215 MB of memory. The model is served by a FastAPI backend and a React web application. Its outputs are estimates of class membership, not proof of authorship.

1. Introduction

AI text generators can now produce fluent essays, summaries and articles in seconds. That creates a practical question for teachers, editors and anyone who reviews writing: how was this text produced? Machine Learning can look for statistical patterns that separate the two kinds of writing, but any answer it gives is an estimate. A system used carelessly can wrongly accuse a real writer.

This report documents an end-to-end project on this problem. The main lesson is that a high score on a test set is not enough on its own. Our first models looked nearly perfect, but only further testing and error analysis revealed how they behaved on human text outside the dataset's style. The final model was selected on that evidence rather than on the highest headline accuracy.

The report follows the structure set by the course brief. Sections 3 to 6 cover the data and features, Sections 7 to 10 the modelling, Sections 11 to 13 the results, benchmarks, errors and interpretation, and Sections 14 and 15 the limitations and conclusions. The appendices describe the web application and how to reproduce the work.

2. Problem Statement and Motivation

2.1 Problem statement

Given a passage of English text, predict whether it is AI-generated or human-written, and report an estimated probability for each class.

Problem definition

ItemDefinition
InputRaw text as a string
Targetgenerated: 0 = human-written, 1 = AI-generated
TaskSupervised binary classification, because each training text carries a label and the output is one of two classes
OutputA predicted class, an estimated Human probability and an estimated AI probability
Expected outcomeA model that clearly beats a baseline, keeps false AI flags low, still detects most AI text, and can be demonstrated on new input

2.2 Motivation

The two possible errors do not cost the same. Missing an AI-written essay is undesirable, but wrongly flagging a person's own work can damage their reputation or grades. Published research has also found that AI detectors can be biased, with one study reporting that GPT detectors often misclassified non-native English writing as AI-generated [1]. For this reason we treat the false positive rate on human text as a primary concern, not only overall accuracy.

Text classification is also a good fit for the course. The problem is real, public labelled data exists, and it requires decisions at every stage of the pipeline.

6. Feature Engineering and Feature Selection

6.1 TF-IDF

Machine Learning models need numbers, so each text is converted to a vector with TF-IDF (Term Frequency – Inverse Document Frequency) [6]. A term scores highly when it appears often in a document but rarely across the collection:

TF-IDF(t, d) = TF(t, d) × IDF(t),   with IDF(t) = ln((1 + n) / (1 + df(t))) + 1

Here t is a term, d a document, n the number of documents and df(t) the number of documents containing t. This is scikit-learn's default smoothed form [7]. With sublinear_tf=True, TF is replaced by 1 + ln(TF), so repeating a word gives diminishing returns. Each document vector is then L2-normalised.

6.2 Original feature recipe

Original TF-IDF settings

ParameterValueDecision

The resulting training matrix has 341,061 rows and 50,000 columns. Only 0.34% of its cells are non-zero, so it is stored in sparse CSR format.

6.3 Final feature recipe

Error analysis (Section 12) showed the original recipe discarded style information. The final model joins two TF-IDF views with a FeatureUnion.

Why these features. Function words such as "because", "very" and "the" carry much of a writer's style while saying little about the topic, so they should be kept. Punctuation tokens capture habits such as comma use. Character 3–5-grams capture spelling, word endings and punctuation patterns, and cope better with unseen word forms.

Snippet augmentation. Each training and validation essay also contributes one random passage of 15–150 words. This creates short examples with the same label, teaching the model to judge passages that are much shorter than a full essay.

6.4 Feature selection

Selection is built into the vectorizers rather than being a separate step. min_df removes rare terms, max_df removes near-universal ones, and max_features keeps the most frequent remaining terms. These rules use only document frequencies and are fitted on training data only. Beyond that, L2 regularisation in the classifier shrinks the weights of less useful features. A statistical filter such as chi-squared was not used, because linear models with regularisation handle high-dimensional sparse features well.

7.4 Preventing data leakage

  • Vectorizers were fitted on training data only and merely applied to the test set.
  • During tuning, TF-IDF sits inside a Pipeline, so each cross-validation fold learns its own vocabulary from its own training portion.
  • The decision threshold was chosen on validation data, not test data.
  • Phase B test records come from the Phase A test part, so they were never used for training.
  • No feature contains target or future information, since the only input is the text.

One weakness remains: held-out data was used to compare versions of the model during Phase B. Section 14 discusses this.

9.1 Models selected

Three algorithms were selected. All are linear models that handle large, sparse TF-IDF matrices efficiently, which matters at 341,061 rows and tens of thousands of features.

9.2 Phase A training

Naive Bayes and an untuned Logistic Regression (C=1.0) were first trained on the 50,000-feature matrix. Linear SVM (C=1.0, max_iter=2000) was trained on the same features. Pipelines with 30,000 features were then tuned for Logistic Regression and Linear SVM (Section 10). Naive Bayes reached 97.92% accuracy and untuned Logistic Regression 99.71%, a large gain over the baseline.

10. Hyperparameter Tuning

Logistic Regression and Linear SVM were tuned with GridSearchCV, using stratified 3-fold cross-validation with shuffling on the training set only, macro F1 as the score, and refitting the best model on all training data. The hyperparameter is C, the inverse of regularisation strength: a smaller C applies stronger regularisation and produces simpler weights, which reduces overfitting. One Logistic Regression fit took about 3.6 minutes, so the grid was deliberately small.

10.1 Decision threshold

The decision threshold is also a tunable setting, and in this problem it has a direct effect on who gets flagged. A first attempt set it at the 99th percentile of human validation scores. This was replaced with a rule that keeps detection explicitly in view: from 0.50 to 0.95 in steps of 0.05, take the highest threshold that still catches at least 90% of AI text on validation data. For the final model, this gives 0.65.

12. Error Analysis

12.1 What the test set could not show

After Phase A, the original recipe was tried on paragraphs known to be human. Two of three were labelled AI, with probabilities of 68.2% and 65.1%. A formal test sentence using "additionally" and "essential" received a displayed AI probability of 100.00%, while an informal sentence received 18.86%. Together these suggested that the model was reacting to formality and vocabulary rather than authorship.

12.2 Why the model made these errors

Causes of false AI flags and the fix for each

12.3 Other findings

  • Dataset patterns. The strongest Human features in the Linear SVM include venus and student_name. The first looks like an essay topic and the second an anonymisation token. Neither says anything general about human writing, which shows the model also learned details of this dataset.
  • Label conflicts. The two train-test pairs of identical text with opposite labels show a small, unavoidable level of label noise.
  • Linear SVM misclassifications. The notebook's Steps 18 and 19 inspect the SVM's incorrect test predictions and their text patterns. [Re-run notebook cells 31–33 and add the error counts and examples]

12.4 Result of the fixes

Measured on held-out data, false flags fell sharply (Section 11.3). Accuracy on same-source essays alone could not have shown this problem, which is why testing outside the dataset's style became a required step.

13. Model Interpretation

Both Logistic Regression and Linear SVM are linear, so each feature's weight shows the direction and strength of its effect. A positive weight pushes towards AI and a negative weight towards human.

13.2 Final model

The weights below were read directly from the saved final model, which has 250,000 features and an intercept of −1.03. The negative intercept means a neutral text starts with a lean towards human.

Strongest character features in the final model

DirectionCharacter n-grams (weight)
Towards AIlike, (3.43), ike,  (3.17), y,  (1.96), e,  (1.88), s,  (1.86)
Towards Human... (−1.91),  so  (−1.73),  go (−1.65),  very (−1.60), becau (−1.53)

Meaningful patterns.

  • Punctuation and function words now dominate, as intended. Formal topic words no longer lead the list.
  • Comma use is prominent on the AI side, for example "like ," and ", which". Repeated periods, hyphens, quotation marks and brackets lean human.
  • "like ," is the strongest AI feature. Some AI samples in the data are conversational (the web app's AI sample includes "Like, let's say"), which may explain this, but it could mislead on casual human writing.
  • "the students" still leans human, showing the essay topics have not disappeared completely.

These weights are correlations in this particular training data. They describe the dataset, not universal rules about AI writing, and a single feature never decides a result.

14. Limitations

Limitations and their effect

LimitationEffect
AI examples are essay-onlyBlogs and news were added as human only, so the model could learn that a non-essay style means human. AI-written blogs or news could be missed. This is the most important limitation
Held-out data reusedPhase B used the same held-out data to compare versions, which the brief warns against. The improvement figures may be slightly optimistic. A fresh test set would be needed for a final, unbiased measure
Same-source test splitPhase A scores near 100% say little about other kinds of writing
Generators changeNewer AI models may write differently from those behind the training data
Subsampled trainingThe final model used 40,000 essays rather than all 341,061 training records, to fit memory limits
Small dry testSix paragraphs (thirteen in the benchmark) show direction only
Limited tuningOnly two values of C were searched, and the final model's C was set by design
Short and edited textVery short text is unreliable. Human-edited AI text, or AI-edited human text, does not fit either class
English onlyThe training data is in English
Probability meaningScores show model confidence and have not been checked for calibration. They are not the percentage of a text written by AI
Application simplificationThe web app shows two labels and does not yet display the notebook's Uncertain outcome

Because of these limits, this model should not be used as the only evidence for any decision about a person's work.

15. Conclusion and Future Work

15.1 Conclusion

This project applied the complete Machine Learning workflow to a real, large text dataset. Against a baseline of 62.76%, three linear models on TF-IDF features reached between 97.92% and 99.95% test accuracy, with tuning by cross-validation. Further testing then showed that a high score on same-source data did not guarantee good behaviour on other human writing.

Error analysis identified four causes, and the final model addressed each with style features, short-text training, wider human data and a validation-chosen threshold. False flags on short human essay snippets fell from 8.5% to 0.4%, and 96.8% of AI essays were still detected. The final model's benchmarks show it is light enough for interactive use, and it runs in a working web application. The most valuable result of the project is therefore not its top score but the process that revealed why that score was not enough.

15.2 Future work

  • Add AI-written blogs, news and other non-essay text, so that style is not confused with source.
  • Evaluate on a fresh test set that played no part in any decision, ideally with newer AI models.
  • Train on more of the available data and widen the hyperparameter search.
  • Check and improve probability calibration, for example with reliability plots.
  • Compare against a transformer model such as DistilBERT, weighing accuracy against the cost of running it.
  • Remove or mask anonymisation tokens such as STUDENT_NAME to reduce dataset-specific signals.
  • Display the Uncertain outcome in the web application.
